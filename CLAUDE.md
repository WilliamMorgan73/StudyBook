# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

StudyBook is a personal study app combining Obsidian-style markdown notes, Notion-style module/assignment/calendar organization, and Anki-style spaced-repetition flashcards. Single-user, no auth. See `README.md`.

Tech stack:
- **Frontend**: React + TypeScript, Vite, Tailwind v4 + shadcn/ui (Nova preset, Radix primitives), React Router, under `frontend/`
- **Backend**: FastAPI (Python), under `backend/`
- **Database**: PostgreSQL via `docker-compose.yml` (service `postgres`, db/user/password all `studybook`)
- **AI integration**: Anthropic API, planned for note summarization, note→flashcard generation, revision scheduling, and semantic note search — not yet implemented

## Commands

All backend commands run from `backend/` and use `uv` (no manual venv activation needed — `uv run` handles it).

```bash
# Install/sync dependencies
uv sync

# Run the dev server (http://localhost:8000, docs at /docs)
uv run uvicorn app.main:app --reload

# Run tests
uv run pytest
uv run pytest tests/test_file.py::test_name   # single test

# Lint
uv run ruff check .

# Database migrations
uv run alembic revision --autogenerate -m "message"
uv run alembic upgrade head
```

Postgres:
```bash
docker compose up -d       # from repo root; starts Postgres on localhost:5432
```

Frontend commands run from `frontend/` and use `pnpm`:
```bash
pnpm install
pnpm dev     # dev server at http://localhost:5173, proxies /api to localhost:8000
pnpm build   # tsc -b && vite build
pnpm lint    # oxlint
```

## Architecture

### Backend layout (`backend/app/`)

- `models/` — SQLAlchemy 2.0 models (`Mapped`/`mapped_column` style). **Import order matters**: individual model modules use bare string forward refs (e.g. `Mapped["Module"]`) for relationships instead of importing each other, to avoid circular imports. `models/__init__.py` is the single place that imports every model module and registers them with SQLAlchemy's mapper registry — always import models via `app.models` (or ensure `app.models` has been imported) before touching `Base.metadata` or querying, or relationship string refs won't resolve.
- `schemas/` — Pydantic request/response models, separate from SQLAlchemy models. `ModuleDetail` (in `schemas/module.py`) is the aggregate payload for the module page: it composes lectures, assignments, submodules, flashcards, and related modules plus computed fields (`current_grade`, `next_lecture_at`) that don't exist as DB columns.
- `crud/` — plain functions, not a generic repository layer. Notably:
  - `crud/grades.py::compute_current_grade` — computes a module's current grade as a weighted average across graded assignments (weighted by `weight_percent` when set, else unweighted mean). This is computed on read, not stored.
  - `crud/spaced_repetition.py::apply_review` — SM-2 spaced-repetition algorithm implementation; mutates a `Flashcard`'s `ease_factor`/`interval_days`/`repetitions`/`due_at` in place based on a 0–5 quality rating.
- `api/routes/` — one router module per resource, all included in `main.py`. `calendar.py` is a read-only aggregate endpoint: it merges `Lecture` and `Assignment` (due-date) rows into a unified sorted list of `CalendarEvent`s rather than being backed by its own table (for lectures it also includes `ends_at`, derived from `duration_minutes`, and `location`, both `None` for assignment-due events). `quick_todos.py` and `quick_note.py` back the Overview page's to-do list and notepad — both are app-wide (no module/assignment scoping), unrelated to the per-assignment `AssignmentTodo`/`notes_markdown`.
- `core/config.py` — `pydantic-settings` `Settings`, reads `.env` (not committed). `core/database.py` defines the SQLAlchemy `Base`, `engine`, and the `get_db` FastAPI dependency.

### Data model relationships

`Module` is the root entity (a course). `Lecture`, `Assignment`, `Submodule`, and `Flashcard` all belong to a `Module`. `Submodule` represents a topic within the module (e.g. "Graph Traversal") and holds one markdown body (`content_markdown`). `Flashcard` optionally belongs to a `Submodule` (flashcards can exist standalone within a module). `ModuleLink` stores "related modules" as a pair of directed rows (one row is inserted for each direction of a relation). `Assignment.weight_percent` is required and the sum of a module's assignment weights is capped at 100% (enforced in `api/routes/assignments.py`, not at the DB level); `Assignment` also has its own `notes_markdown` body, `todos` (`AssignmentTodo`, a simple ordered checklist), and `attachments`.

`AppSettings` and `QuickNote` are both single-row (`id=1`, get-or-create) tables for app-wide state — settings (`max_credits`, `theme_mode`, `skin`, `table_alignment`, `note_font_size`, `keybind_bold`/`keybind_italic`/`keybind_code`/`keybind_wikilink`) and the Overview page's freeform notepad content, respectively, kept as separate tables since one is configuration and the other is user content. All the `AppSettings` fields are flat scalar columns with Python-level defaults (matching `theme_mode`/`skin`'s existing style) rather than a JSON blob, even though four of them (the keybinds) are conceptually one group — `keybind_*` stores a raw CodeMirror keymap string per action (e.g. `"Mod-b"`, `"Mod-Shift-k"`), consumed by `MarkdownEditor`'s `formattingKeymap`. `QuickTodo` is a plain multi-row table (no singleton pattern, no FK) for the Overview page's to-do list.

`Attachment` is polymorphic: `submodule_id` and `assignment_id` are both nullable FKs and exactly one is set, by construction — there are two upload endpoints (`POST /submodules/{id}/attachments`, `POST /assignments/{id}/attachments`), both going through the shared `crud/attachments.py::store_upload`, rather than a DB-level constraint enforcing the XOR. Files are saved to disk under `backend/uploads/submodules/<id>/` or `backend/uploads/assignments/<id>/` (namespaced this way so a submodule and an assignment with the same numeric id can't collide) with a UUID filename; `Attachment.file_path` stores the on-disk path and `Attachment.url` (a computed property, not a column) is what the API exposes for fetching it back — served by the `/uploads` static mount in `main.py`. `DELETE /attachments/{id}` (`api/routes/attachments.py`) removes both the DB row and the on-disk file.

Submodules support Obsidian-style `[[Wikilink]]` / `[[Title|Alias]]` references to other submodules, resolved on demand rather than stored: there is no link table (an earlier `SubmoduleLink` table plus a "Linked mentions"/backlinks panel was tried and then deliberately removed — backlinks matched Obsidian but not how notes get used here, so linking stayed strictly one-directional). `crud/submodule_links.py::resolve_wikilink` takes a raw title and the current module id, supports `"Module Title/Submodule Title"` disambiguation, and otherwise prefers a same-module match before falling back to the first match anywhere; `GET /submodules/resolve?title=&module_id=` (`api/routes/submodules.py`) wraps it for click-to-navigate and 404s when unresolved. `GET /submodules` is a separate lightweight cross-module index (`SubmoduleIndexEntry`: id/title/module_id/module_name, no `content_markdown`/attachments) for a future link picker, with an optional `search` filter.

### Alembic

`alembic/` is initialized in `backend/`. `env.py` imports `app.models` (to populate `Base.metadata`) and reads the DB URL from `app.core.config.settings.database_url` rather than `alembic.ini`. Use `uv run alembic ...` for all migration commands, from `backend/`.

### Frontend layout (`frontend/src/`)

- `lib/api.ts` — typed fetch client for the backend (paths are relative, e.g. `/modules`; the Vite dev server proxies `/api/*` to `localhost:8000`, stripping the `/api` prefix — see `vite.config.ts`).
- `lib/useAsync.ts` — small hook wrapping a promise-returning fetcher into `{ data, loading, error }`, re-running when its deps array changes.
- `pages/` — one component per route: `Overview` (`/`), `ModulePage` (`/modules/:moduleId`), `AssignmentPage`, `SubmodulePage`. There is no module-settings route — `ModuleSettingsDialog` (in `components/`) is a modal opened from `ModulePage`, not a page.
- `components/` — page-level building blocks (dialogs, `MonthCalendar`, `ModuleWeekCalendar`, `Countdown`, `ModuleSettingsDialog`, `RadialProgress`/`ModuleProgressRing`) plus `components/ui/` for shadcn/ui primitives (generated via `pnpm dlx shadcn@latest add <name>`).
- `ModulePage`'s whole body is `Card`-wrapped sections (Schedule, Assignments, Submodules, Flashcards, Related modules) with the same spacing scale as `Overview` (`space-y-8 px-8 py-8`, `grid gap-6`), rather than bare `<section>`s — matching Overview's visual language was an explicit ask, since the two pages had drifted apart. There's no standalone "Lectures" list anymore: it was showing the same recurring-series data as Schedule in a different format (a pattern summary vs. that pattern's actual upcoming occurrences), so it was cut in favor of `ModuleWeekCalendar` (a fixed, non-navigable two-week grid — this week + next, Monday-start, click a day to see that day's lecture(s) with time range/location below) sourced directly from `module.lectures` (no `getCalendar` fetch needed, since it only shows this module's lectures, not assignment due dates — those already have their own list in Assignments). Full lecture-series management (add/edit/delete a series) still lives in `ModuleSettingsDialog`'s Lectures tab; `ModuleWeekCalendar` is read-only.
- Recurring lectures are a frontend-only convenience: `ModuleSettingsDialog`'s add-lecture form generates one `Lecture` row per occurrence via repeated `POST /lectures` calls (spaced 7 or 14 days apart) rather than the backend storing a recurrence rule — each occurrence stays independently editable/deletable afterward.
- `ModuleSettingsDialog` uses the same category-sidebar shell as `AppSettingsDialog` (General, Lectures). General's credits field is validated against the app-wide `max_credits` (fetched via its own `useAsync(() => getAppSettings())`) minus every *other* module's credits (fetched via its own `useAsync(() => listModules())`, filtered by id) — client-side only, unlike `Assignment.weight_percent`'s 100%-cap, which is enforced server-side (in `api/routes/assignments.py`, still not a DB constraint). `AddModuleDialog`'s credits field on module creation has no such check. The Lectures tab's "Repeats" field uses `components/ui/select.tsx` (shadcn/ui's Select, added via `pnpm dlx shadcn add select` — see the shadcn CLI quirk note below), not a plain `<select>`: a native `<select>`'s dropdown list is rendered as OS/browser chrome outside the page's own paint layer, so it can't be reliably themed with CSS (`color-scheme` alone wasn't enough — see `index.css`) or even screenshot-verified, whereas Radix's `Select` renders its popup as ordinary styled DOM.
- Module cards and the module page's hero both show `ModuleProgressRing`: a donut built from `completion_progress` (`completed_fraction`/`achieved_fraction`, weight-based — `crud/grades.py::compute_completion_progress`, computed server-side alongside `assignment_progress`), not raw assignment counts. `completed_fraction` sums `weight_percent` for assignments that are `submitted` or `graded` (out of the module's full 100%, not out of whatever's been created so far); `achieved_fraction` additionally scales each graded assignment's weight by its `grade_earned/grade_max`. The ring shows the full module accent color for `achieved_fraction` and a faint (`4d` alpha) shade of it for the `completed_fraction − achieved_fraction` remainder (work turned in/graded but short of full marks) — whatever hasn't been submitted yet is just the ring's plain unfilled remainder. `assignment_progress` (graded/in_progress/not_started counts) still exists separately for textual breakdowns (e.g. the Overview Progress card's hover legend), it's just no longer what the ring itself renders.
- The Overview page's Calendar card (`pages/Overview.tsx`) keeps showing the previously-loaded month's events while the next month's are in flight, rather than gating on `calendar.data` (the raw `useAsync` result) directly: `useAsync` nulls `data` the instant its `deps` array's identity changes, which for the calendar is `gridRange` — a new object every month switch — so gating render on `calendar.data` truthiness unmounted the whole card in favor of a loading skeleton on *every* month change, a visible "blink". A local `displayedEvents` state, updated via a `useEffect` only when `calendar.data` is non-null, decouples "what's rendered" from "is a fetch in flight" (stale-while-revalidate) without changing `useAsync`'s shared behavior, which other pages rely on as-is; the skeleton now only shows on the true first load (`calendar.loading && !displayedEvents`). Verified via a `MutationObserver` watching for `[data-slot="skeleton"]` across several month-forward clicks: never fires.
- The Overview page's calendar day list (`pages/Overview.tsx`) is click-to-expand per event: clicking a day selects it and lists that day's events (as before), and clicking an individual event within that list toggles an inline detail block — start–end time and location for a lecture, a direct link for an assignment due date — tracked by a single `expandedEventKey` string state, reset whenever the selected day changes. That list sits in a fixed-height (`h-24`), independently-scrolling container so expanding an event never changes the Calendar card's own height — necessary because the row uses CSS Grid's default `stretch`, so any card growing taller stretches every card in the row with it.
- The Overview page's top row (`lg:grid-cols-4`) has two 2-card flex columns beside the Calendar: Upcoming assignments + To-do, and a Progress card + Notepad. The Progress ring uses `RadialProgress` directly (not `ModuleProgressRing`, which only takes one color) with an achieved+shortfall segment pair *per module* (same `completed_fraction`/`achieved_fraction` split as the per-module ring, in that module's own color), each pair sized by the module's share of `credits` summed across all modules (`m.credits ?? 1` as a fallback weight for modules with no credits set, so the ring never goes empty just because credits weren't filled in). It fills most of its card (136px) with the overall achieved % as a center label by default; the breakdown (overall achieved/submitted % plus a per-module achieved-% legend) is a second `absolute inset-0` layer that fades in on hover via the `group-hover/card:opacity-100` + `Card`'s own built-in `group/card` class, swapping places with the default label (`group-hover/card:opacity-0`) rather than showing both at once.
- `components/MarkdownEditor.tsx` wraps `@uiw/react-codemirror` (+ `@codemirror/lang-markdown` with `@lezer/markdown`'s `GFM` extensions) to give `SubmodulePage` an Obsidian-style *live preview* editor: a `ViewPlugin` walks the Lezer markdown syntax tree on every doc/selection change and hides formatting marks (`HeaderMark`, `EmphasisMark`, `CodeMark`, `StrikethroughMark`, `QuoteMark`) via `Decoration.replace` on every line except the one the cursor is on, while styling the surrounding node (heading size, bold, italic, inline code, strikethrough, blockquote) unconditionally via `Decoration.mark`/`Decoration.line`. The editor's own `syntaxHighlighting` is turned off in `basicSetup` (its default color scheme clashes with the app's monochrome Nova theme) in favor of these hand-picked classes. `sourceMode` (toggled from `SubmodulePage`'s header) just omits the live-preview `ViewPlugin` from `extensions`, leaving plain-text markdown. There's no separate read-only view anymore — the editor is always live, saving on blur like the rest of the app's inline-edit fields.
  - **Focus tracking is hand-rolled, not `view.hasFocus`/`.cm-focused`**: in this component tree those never reliably toggled, which both hid the cursor permanently and left line 1's marks visible until the first click. Fixed with an explicit `StateField<boolean>` (`focusedField`) updated by a `StateEffect` dispatched from React's `onFocus`/`onBlur` (not CodeMirror's own focus events, and debounced one tick via `setTimeout` — clicking, especially into a blank line, can fire several synchronous focus/blur events before settling, and dispatching on each intermediate one was itself feeding the thrashing since every dispatch recomputes decorations), an `EditorView.editorAttributes` facet that adds a `cm-live-focused` class from that field, and a theme rule keyed off that class (not `.cm-focused`) to show the cursor. `buildDecorations` reads `state.field(focusedField, false)` instead of `view.hasFocus` for the same reason. Theme rules that toggle on a class *of the editor root itself* (like this one) must use `EditorView.theme`'s `&` prefix (`'&.cm-live-focused .cm-cursor'`, matching the existing `'&.cm-editor.cm-focused'` outline-removal rule) — a bare `.cm-live-focused .cm-cursor` selector gets an implicit ancestor scope prepended by `theme()` and can never match, since the scope class and `cm-live-focused` land on the same element rather than one being a descendant of the other.
  - Hiding `HeaderMark`/`QuoteMark` alone leaves their trailing space behind (e.g. "# " → " Heading", a stray gap before the text once the `#` itself disappears) — `skipTrailingSpace` extends the hidden range through that one space too, via `MARK_NODES_CONSUME_TRAILING_SPACE`.
  - The cursor's default 1.2s blink is disabled (`drawSelection({ cursorBlinkRate: 0 })`, added alongside `basicSetup`'s own `drawSelection` — `selectionConfig`'s facet combines multiple `cursorBlinkRate`s with `Math.min`, so 0 always wins regardless of extension order) because a blank line gives the eye nothing else to anchor on, so the normal on/off blink reads as "the cursor is gone" far more often there than on a line sitting next to text.
  - Spellcheck goes through `EditorView.contentAttributes` rather than a prop, since `@uiw/react-codemirror` has no prop that reaches CM6's actual `.cm-content` node — unrecognized props land on the outer wrapper div instead. `InlineCode` decorations override it back off per-node via their own `attributes: { spellcheck: 'false' }`, since code isn't prose.
  - `buildFormattingKeymap(keybinds)` (`Prec.highest`, so it wins over `basicSetup`'s default keymap regardless of extension order) builds a `keymap.of([...])` from `AppSettings.keybind_bold`/`keybind_italic`/`keybind_code`/`keybind_wikilink` (falling back to `DEFAULT_KEYBINDS` in `lib/keybinds.ts` — `Mod-b`/`Mod-i`/`Mod-e`/`Mod-Shift-k` — when settings haven't loaded yet), each wrapping/unwrapping the selection via `toggleWrapCommand`. Rebuilt fresh per render (unlike the module-level `slashCommandKeymap` below) since the bindings are user-configurable and can change without a reload; `keymap.of()` isn't a `StyleModule`, so rebuilding it per render has no leak/caching concern the way a fresh `EditorView.theme()` would (see the `dynamicAttributes` note further down). Plain Mod-K is deliberately never the wikilink *default* — it's the browser's own "focus address bar" shortcut and never reaches the page outside automated testing — but nothing stops a user from rebinding onto it themselves via Settings.
  - `\bold`, `\link`, `\code`, `\codeblock`, `\image`, and `\table<N>x<M>` are text-triggered "slash commands": typing one and pressing Space/Enter expands it in place. `runSlashCommand` (bound to Space and Enter via the module-level `slashCommandKeymap`, `Prec.highest`) scans backward from an empty cursor for a `\word` token anchored to start-of-line/whitespace (`SLASH_TRIGGER_PATTERN`), skips matches inside code (`isInsideCode`), and does a single `view.dispatch` that both deletes the token and inserts the expansion — one undo step reverts it fully. `bold`/`link`/`code`/`codeblock`/`image` are table-driven (`SIMPLE_SLASH_COMMANDS`: a `{before, after}` pair with the cursor placed in between, the same shape `toggleWrapCommand` already uses for its empty-selection case); `table<N>x<M>` is parsed by `TABLE_SLASH_PATTERN`, capped at `MAX_TABLE_DIMENSION` (12) per side, and generates N columns × M **data rows** (the header row and its `---` divider are always additional) via `buildTableMarkdown`, which also selects the placeholder text `"Header 1"` so it's ready to be typed over. No new decoration logic is needed for any of this — the inserted markdown is picked up by the same `liveMarkdown`/`tableDecorations` machinery that renders hand-typed markdown. One caveat baked into `buildTableMarkdown`: a data cell that's *entirely* whitespace never gets a `TableCell` node from `@lezer/markdown`'s table parser (it only tokenizes non-whitespace runs between `|`s), so an empty-looking cell has to contain `EMPTY_CELL` (a zero-width space, `U+200B`) rather than `''` — otherwise the row's cells silently vanish from `getRowCells`'s output (reproduced live: row count matched, but every row's cells came back empty). `U+200B` survives `getRowCells`'s own `.trim()`, since JS's `trim()` doesn't strip that character (a Unicode "Format" character, not a space separator).
  - `[[Title]]` / `[[Title|Alias]]` wikilinks aren't CommonMark/GFM syntax, so the Lezer parser produces no node for them — `addWikilinkDecorations` finds them with a plain regex scan (`WIKILINK_PATTERN`) instead of a syntax-tree walk, skipping matches inside inline/fenced code (`isInsideCode`), and hides the `[[`/`|Alias]]`/`]]` delimiters on unfocused lines the same way mark nodes are hidden. Cmd/Ctrl+click on a rendered wikilink (`wikilinkClickHandler`) calls `onNavigateWikilink` (wired from `SubmodulePage` to `resolveWikilink` in `lib/api.ts`, hitting `GET /submodules/resolve`); an unresolved link is a silent no-op rather than an error. `SubmodulePage.handleNavigateWikilink` `await`s `saveContent()` before calling `navigate()` — Cmd/Ctrl+click fires `navigate()` straight from this click handler rather than through a DOM blur, so `MarkdownEditor`'s `onBlur={saveContent}` never runs, and without the explicit save the route swap would unmount the page (discarding any unsaved edits) before they were persisted.
  - `HorizontalRule` (`---`) and `Image` (`![alt](src)`) nodes replace themselves with a `HorizontalRuleWidget`/`ImageWidget` (a styled `<div>`/`<img>`) on unfocused lines, same cursor-line exemption as every other live-preview decoration.
  - GFM `Table` nodes render as a real `<table>` via `TableWidget`, but live in their own `tableDecorations` `StateField` rather than `buildDecorations`/`liveMarkdown`'s `ViewPlugin` — CodeMirror disallows a `ViewPlugin` from providing both block decorations and decorations that replace a line break, and a table spans multiple lines, unlike every other decoration in this file. `TableRowSource`/`getRowCells` read `TableHeader`/`TableRow`/`TableCell` children without importing `@lezer/common`'s `SyntaxNode` type directly (not resolvable under this project's pnpm layout — same workaround as `WalkableNode`, used by `isInsideCode`).
  - `FencedCode`/`CodeBlock` (fenced and 4-space-indented code) get a per-line background/monospace box (`cm-codeblock`, rounded via `cm-codeblock-start`/`-end` on the first/last line) that stays visible regardless of cursor position — only the fence marks themselves (plain `CodeMark` nodes, already covered by `MARK_NODES`) hide/reveal per line. `CodeInfo` (the fence's language string, e.g. `python`) gets a small muted/uppercase `cm-code-lang` style instead of rendering as code text, and spellcheck is disabled per code-block line via the line decoration's own `attributes`, same rationale as `InlineCode`.
  - `$...$` (inline) and `$$...$$` (display, often multi-line) math aren't CommonMark/GFM syntax either — `BLOCK_MATH_PATTERN`/`INLINE_MATH_PATTERN` find them with a plain regex scan, same approach as wikilinks, and render via KaTeX (`katex.render` into a widget's DOM node directly, not `renderToString`, so there's no need to trust/sanitize an HTML string). Block math needs its own `mathBlockDecorations` `StateField` for the same multi-line reason as tables; inline math is scanned per visible range inside `buildDecorations` alongside wikilinks (`addInlineMathDecorations`), and skips any match inside a code node (`isInsideCode`) or inside an already-matched block-math span (`findBlockMathRanges`, called once per build so `$$x$$` doesn't also get read as inline math via its own middle two `$`s). The inline pattern additionally requires non-whitespace immediately inside both delimiters (Obsidian/Typora's own heuristic) so plain currency like "$5 and $10" isn't mistaken for math. Both widgets fall back to plain text on a KaTeX parse error instead of throwing.
  - `fontSize`/`tableAlign` props (from `AppSettings.note_font_size`/`table_alignment`) are applied as CSS custom properties (`--note-font-size`, `--note-table-margin-x`) via `buildDynamicAttributes`, an `EditorView.editorAttributes` extension setting an inline `style` on `.cm-editor`, with the *static* module-level `editorTheme` reading them through `var(..., fallback)`. This is deliberately **not** a fresh `EditorView.theme({...})` built per render/prop-change: `EditorView.theme()` mounts a real, permanent CSS rule into the document the first time it sees a given *object*, and CodeMirror never garbage-collects that rule just because a later reconfigure stopped using it (themes are normally a handful of stable, reused objects, e.g. swapped via a `Compartment`) — building one fresh whenever `fontSize`/`tableAlign` change leaves multiple competing rules for the same selector in the stylesheet, and which one wins the cascade becomes render-history-dependent rather than "whatever the current props are" (reproduced live: table centering silently not applying because an older, since-abandoned rule kept winning). `EditorView.editorAttributes`, by contrast, just replaces a plain element attribute on reconfigure — no stylesheet growth, no cascade ambiguity.
  - The editor **grows with its content and lets the page scroll**, rather than scrolling internally: `.cm-scroller`'s `flex: '1 1 auto'` (not `'1 1 0px'`) makes its *hypothetical* size for `.cm-editor`'s auto-height sizing track real content height. With `flex-basis: 0`, the hypothetical size was 0 regardless of content, so `.cm-editor` always resolved to exactly `minHeight` (70vh) no matter how long the document was, and `.cm-scroller` (bounded to that height, with the CodeMirror base theme's default `overflow: auto`) grew its own internal scrollbar instead of ever pushing the page taller — reproduced live via `getBoundingClientRect()`: both boxes measured exactly 70vh with 3000+px of actual content behind them. `flex-basis: auto` (plus explicit `overflow: 'visible'` on `.cm-scroller`, belt-and-braces) fixes long documents without reintroducing the invisible-cursor bug on short ones: a short document's hypothetical size is still less than `minHeight`, so flex-grow still stretches `.cm-scroller` to fill it exactly as before.
- `components/Countdown.tsx` (renamed from `NextLectureCountdown`) is shared between `ModulePage`'s hero (next lecture) and `AssignmentPage`'s hero (due date) via `noneLabel`/`arrivedLabel` props, since the two contexts need different empty/arrived text ("None scheduled"/"Starting now" vs "No due date"/"Due now").
- `AssignmentPage` no longer has an inline "Settings" edit section or a status/grade dropdown: `AssignmentSettingsDialog` (title/due date/weighting/description/delete, no sidebar tabs — there's only one category's worth of fields) mirrors `ModuleSettingsDialog`'s dialog chrome, and `components/AssignmentCompletion.tsx` owns status/grading entirely through a small state machine keyed off `assignment.status`: not_started/in_progress → a "Mark complete" button (sets `status: 'submitted'`) → "Uncomplete" (back to `not_started`, clearing `grade_earned`/`grade_max`) or "Enter grade" (an inline score/out-of form that sets `status: 'graded'`) → the saved grade display, with "Edit grade"/"Uncomplete" below it. This is a deliberate simplification: the old settings form's status `<select>` could set `in_progress` directly, which is no longer reachable from the UI (still a valid enum value, just not exposed).
- `SubmodulePage`'s title is edited inline in the `PageHeader` (click the title to turn it into a text input, Enter/blur to save, Escape to cancel) rather than through the settings dialog — the settings dialog now only holds the delete action.
- **Theming**: `lib/theme.ts` defines `SKINS` (`default`/`slate`/`sepia`, each with light+dark CSS variable blocks in `index.css` under `:root[data-skin="…"]` / `:root[data-skin="…"].dark`) and `applyTheme(mode, skin)`, which toggles the `.dark` class and sets `documentElement.dataset.skin` (resolving `theme_mode: "system"` via `prefers-color-scheme`). `App.tsx` calls `useApplyTheme()` once to apply the persisted `AppSettings` on load and keep "system" mode listening for OS changes. `AppSettingsDialog`'s Appearance tab calls `applyTheme` directly on click (before the PATCH resolves) for instant feedback, and tracks `themeMode`/`skin` in **local state seeded from the `settings` prop**, not read from the prop directly — the dialog's `onChanged` callback drives the same `reloadKey` as the modules list on the Overview page, and `useAsync` nulls its data immediately on every dependency change, so a prop-driven read would flash-unmount the dialog (wrapped in `{appSettings.data && <AppSettingsDialog .../>}`) on every single click. `max_credits` still goes through that reload on save since module cards depend on it; appearance changes don't call `onChanged` at all.
  - `index.css`'s `:root`/`.dark` blocks also set `color-scheme: light`/`dark`. Without it, the browser has no way to know the page itself is dark (a dark `--background` alone doesn't imply that), so native form UI — `<input type="date"/"time">` pickers, checkboxes, number-input spinners — kept the browser's light-mode default regardless of the app's own theme. This does **not** cover a native `<select>`'s dropdown *list*, though: that's rendered as OS/browser chrome outside the page's paint layer, where `color-scheme` support is inconsistent and, worse, unverifiable via a page screenshot (it simply isn't captured) — the one native `<select>` in the app was replaced with `components/ui/select.tsx` instead (see the `ModuleSettingsDialog` note above) rather than relying on this.
  - `index.css` also hides the native up/down spinner on every `input[type="number"]` app-wide (`-webkit-appearance: none` on the WebKit spin buttons, `-moz-appearance: textfield` for Firefox) — it's unstyleable and always looks like plain OS chrome, clashing with the rest of the app's custom-styled `Input`. Fixed once at the shared styling layer rather than touching each of the ~10 `type="number"` call sites; typing and arrow-keys still work, just no visible click-to-increment affordance.
  - `index.css` also defines a thin, theme-aware scrollbar (`scrollbar-width`/`scrollbar-color` for Firefox, `::-webkit-scrollbar-*` for everything else, using `--border`/`--muted-foreground`) applied globally, in place of the browser default — relevant because `MarkdownEditor` deliberately has *no* internal scroll of its own (see the `MarkdownEditor` notes above), so the page's own scrollbar is what users actually see while editing a long note.
- `AppSettingsDialog` (opened from the Overview page's header) has a category sidebar (Appearance, General, Keybinds, AI Integration, Data) rather than a flat form — General holds `max_credits` (the original single setting), AI Integration and Data are placeholder panels for planned work (see `README.md`'s AI integration section). Appearance holds Theme/Skin (both pre-existing, live-apply-on-click) plus `table_alignment` and `note_font_size`, added the same way: `table_alignment` is a `Tabs` toggle like Theme's, live-applied; `note_font_size` is a plain number `Input` (10–32px) that commits `onBlur` rather than per-keystroke, matching the app's established blur-to-save convention. Keybinds renders one `KeybindInput` (`components/KeybindInput.tsx`) per entry in `lib/keybinds.ts`'s `KEYBIND_ACTIONS` (bold/italic/code/wikilink) — click the button to start "recording", the next non-modifier keydown is captured via `captureKeybind` into a CodeMirror keymap string (`Mod-Shift-k` order: Mod, then Shift, then Alt, then the key), Escape cancels. Each row shows a non-blocking "Also used by X" warning (computed in the parent by comparing all four current values) when two actions share a combo, and a reset-to-default button that appears only when the value differs from `DEFAULT_KEYBINDS`. Like Theme/Skin, none of these three call the dialog's `onChanged` — `useAsync`'s null-on-every-dependency-change would otherwise flash-unmount the dialog mid-edit (see the note on `useAsync` above) — so reopening the dialog within the same page load can briefly show a stale value for a field just changed until the page itself reloads; functionally harmless since `MarkdownEditor` reads fresh settings independently via its own `useAsync` on `SubmodulePage`.

### Desktop shell (`frontend/src-tauri/`)

An optional Tauri wrapper (generated via `pnpm tauri init`) gives the existing Vite frontend a chromeless native window (title "StudyBook", 1280×832, min 900×600, identifier `com.willmorgan.studybook`) — dev-only, no backend/database changes: it points at the same `localhost:5173` dev server, which already proxies `/api` and `/uploads` to `localhost:8000` per `vite.config.ts`. Run with `pnpm tauri dev` (from `frontend/`, needs `pnpm dev` conventions but not a separately-running dev server — `tauri dev` starts it) after a Rust toolchain is installed. `pnpm tauri build` produces working `.deb`/`.rpm` bundles; AppImage packaging is unresolved (linuxdeploy needs fuse2, not available alongside fuse3 on this machine) and isn't a current goal since distributable packaging isn't this phase's focus.

### Known quirk: shadcn CLI path alias resolution

This project's Vite template splits `tsconfig.json` into `tsconfig.app.json`/`tsconfig.node.json` via project references; the root `tsconfig.json` only has `references`, no `compilerOptions`. The `shadcn` CLI resolves the `@/*` import alias by reading the root `tsconfig.json` only, so without `paths` duplicated there too, `shadcn add` writes new component files into a literal `./@/` directory instead of `./src/`. The root `tsconfig.json` in this repo already carries a `paths` block for this reason — if `shadcn add` ever creates a stray `frontend/@/` directory again, move its contents into `src/` and delete it.
