# Frontend (`frontend/src/`)

For the markdown editor, see [`markdown-editor.md`](markdown-editor.md).

## Layout

- `lib/api.ts`: typed fetch client with relative paths (`/modules`); Vite proxies `/api/*` (prefix stripped) and `/uploads` to `localhost:8000`.
- `lib/useAsync.ts`: `useAsync(fetcher, deps, { keepPreviousData? })` → `{ data, error, loading, refetch }`. Tested in `useAsync.test.ts` (jsdom, `renderHook`).
  - `loading` means "nothing to show yet", so gating a skeleton on it only blanks a first load.
  - `refetch()` re-runs the current fetcher and keeps `data` on screen until the response lands; use it after saves instead of a reload counter. Stable identity (safe as `onChanged={refetch}`); resolves (never rejects) once state is updated.
  - A deps change resets `data` to null (a different resource, e.g. another module id) unless `keepPreviousData: true`, which keeps the old data until the new arrives (Overview calendar months).
  - Only the latest request's result applies; superseded and post-unmount responses are dropped. A failed refresh sets `error` but keeps `data`, so pages treat "no data and not loading" (not `error`) as the failed-first-load state.
- `lib/progress.ts::progressRingSegments`: turns `completion_progress` into the two-arc ring (full accent color for `achieved_fraction`, `4d`-alpha shade for `completed_fraction − achieved_fraction`, unfilled remainder = not submitted). Used by `ModuleProgressRing` and the Overview Progress card.
- `lib/lectureSchedule.ts`: lecture-series helpers for `ModuleSettingsDialog`, including `groupLectures` (see Lectures).
- `pages/`: `Overview` (`/`), `ModulePage` (`/modules/:moduleId`), `AssignmentPage`, `SubmodulePage`. Module/assignment settings are modal dialogs in `components/`, not routes.
- `components/ui/`: shadcn/ui primitives, added with `pnpm dlx shadcn@latest add <name>` (see the path-alias quirk in `CLAUDE.md`).
- Use `components/ui/select.tsx` (Radix), never a native `<select>`: the native dropdown list is OS chrome that CSS can't theme and screenshots can't capture.

## Pages

**Overview.** A customisable dashboard of widgets on a 12-column `react-grid-layout` grid (`components/dashboard/`).
- `lib/dashboardLayout.ts` defines a `Board` (widget registry + default layout) and the pure layout helpers, which take the board as their first argument. The Overview's board is `OVERVIEW_BOARD` there: the widget registry (`WIDGETS`: title, menu description, min/default size), `DEFAULT_LAYOUT` (Calendar over Day agenda; Upcoming + To-do; Progress + Notepad; Modules across the bottom). The layout is saved as `app_settings.dashboard_layout` (`null` = default; saving a layout equal to the default stores `null`). The backend only checks the shape, so always read it through `normalizeLayout`, which drops unknown/duplicate ids and clamps sizes. Adding a widget is frontend-only: a `WIDGETS` entry, a `WidgetId`, and a body in Overview's `WIDGET_BODIES`.
- Edit mode lives in `useLayoutEditor(board, stored, persist)` plus the `LayoutEditControls` header buttons, shared with ModulePage. "Edit layout" holds a `draft`: widgets drag by their header (`DRAG_HANDLE_CLASS`) and resize from the right edge, bottom edge or corner; the ✕ removes, "Add widget" lists `hiddenWidgets`, Reset sets the default, Cancel drops the draft, Done PATCHes it. Widget bodies ignore the pointer while editing. Grid handle/placeholder styles are in `index.css` under `.dashboard-grid`.
- `DashboardGrid` measures its own width: under 900px the widgets stack in one column in reading order (`stackedOrder`) at their grid heights, instead of the grid.
- `DashboardWidget` is the shared card: it fills its cell and its body scrolls and is an `@container`, so widgets adapt with container queries (Modules: one column when narrow, up to four when wide). Sizes that must be numbers use `lib/useElementSize.ts` (Progress ring size, calendar title lines).
- Overview fetches modules and app settings once and shares them, plus the calendar state from `useOverviewCalendar` (month, selected day, expanded event, busy toggle, the `/calendar` fetch), through `overviewContext.ts`. The Calendar and Day agenda widgets both read that state; when the Day agenda widget isn't placed, the Calendar widget shows the selected day's list inline under its grid.
- Calendar fetch uses `keepPreviousData`, so the previous month stays on screen while the next loads; skeleton only on first load. `MonthCalendar`'s `fill` prop stretches the weeks to the widget's height (rows never below `min-h-11`); once a cell is ≥96px wide it lists as many event titles as its height fits ("+N more" for the rest) instead of marker dots.
- Busy time (`kind="busy"`, from personal events and calendar feeds) shows as a muted dash marker (`EventMarker`: grey, or the feed's `color` faded; `calendarEventColor` picks a feed event's own colour over its module's), always after other markers in a day cell (`busyLast`). Feed events with `all_day` read "All day" in the Day agenda. The legend's "Busy" button hides/shows it (`visibleCalendarEvents`), remembered in `localStorage`. Personal busy events repeat their `id` and feed events number separately, so event keys use `calendarEventKey` (`feed` or kind + id + start).
- `useOverviewCalendar` calls `POST /calendar-feeds/refresh-stale` once on mount and refetches the calendar only if a feed actually synced; the cached events render meanwhile. `ModuleWeekCalendar` never shows busy time: it reads `module.lectures`/assignments, not `/calendar`.
- Day agenda (`DayAgenda`): click a day to list its events, click an event to toggle inline details (tracked by `expandedEventKey`, reset on day change).
- Progress ring: `RadialProgress` with one achieved+shortfall pair per module in its own color, sized by credit share (`m.credits ?? 1` fallback); the ring grows with the widget.
- Today's revision lists today's `RevisionSession`s with done ticks (also refetching the calendar); Flashcards due groups `GET /flashcards/due` by module, each with a `StudySession` button.

**ModulePage.** A module-tinted banner (`components/ModuleBanner.tsx`), then a customisable board like the Overview's. The banner's stats (and their order), ring, tint and size come from `module.banner` through `lib/moduleBanner.ts::normalizeBanner` (null = `DEFAULT_BANNER`, the old fixed banner); while the layout is being edited it shows "Customise banner", which opens `ModuleBannerDialog` and saves straight away. The board is `MODULE_BOARD` in `lib/moduleLayout.ts` (default: Schedule over Submodules, Assignments, Flashcards), saved per module as `modules.dashboard_layout` via `updateModule` (`null` = default). Widget bodies are in `components/dashboard/ModuleWidgets.tsx` and read the page's data through `ModuleContext` (`moduleContext.ts`); header actions (Add submodule, Add assignment, Study) go in `DashboardWidget`'s `action`. The page is keyed by module id so a draft doesn't carry over. Schedule is `ModuleWeekCalendar`: a fixed two-week grid (this week + next, Monday start); the selected day lives in the context, and its events (`ModuleDayList`) sit beside the grid unless the Day agenda widget is placed, mirroring the Overview's Calendar/Day agenda. Progress splits the ring by assignment (`lib/progress.ts::assignmentRingSegments`) and highlights on hover like the Overview's. Grade breakdown's target maths is `lib/grades.ts`. To-do and Notepad are the module's own (`QuickTodoList moduleId`, `module.notes` via `NotepadArea`); the Overview's To-do widget shows General plus every module's to-dos under a heading per module, with a filter remembered in `localStorage`.

**AssignmentPage.** Module-tinted header (title, due/weight, description, countdown, completion, "Covers" chips), then two columns: the notes are a full `MarkdownEditor` on the left (saves on blur/commit like SubmodulePage; `![[file]]` embeds and paste/drop uploads use the Assignment's Attachments), and a sticky right rail with `AssignmentChecklist` (one bordered box, progress bar in the module color), `RevisionPlan` for exams, and `AttachmentEmbeds` (PDF/image/video/audio previewed inline; PPTX/other as a row). `AssignmentSettingsDialog` holds title/due date/weighting/description/delete. `AssignmentCompletion` owns status as a state machine on `assignment.status`: not_started/in_progress → "Mark complete" (`submitted`) → "Uncomplete" (back to `not_started`, grade cleared) or "Enter grade" (`graded`) → grade display with "Edit grade"/"Uncomplete". `Countdown` is shared with ModulePage via `noneLabel`/`arrivedLabel`.

**Revision plan.** Exam Assignment pages only show `RevisionPlan`: "Plan revision" (`PlanRevisionDialog`: start date, weekday toggles, Radix session-length `Select`; form checks in `lib/revision.ts`, the backend's not-enough-time `detail` shown as-is) until a plan exists, then the sessions with done ticks, "Replan" and "Clear plan". Replan reuses `PlanRevisionDialog` with `mode="replan"`, prefilled by `replanForm` (the plan's weekdays and latest session length, from today). `GET …/revision-plan/status` drives an amber nudge (`replanReasons`: missed sessions, topics that got weaker/stronger) and "Missed" labels; ticks, replans and clears refetch it. `?session=<id>` opens `RevisionSessionDialog` (done tick, topics with a Weak/Fair/Strong label, weakest cards, and `guidance_markdown` once #13 writes it); calendars link there via `revisionSessionUrl`. Sessions are a ring `EventMarker` (filled when done) on the Overview calendar (tick in the expanded day-list row) and on `ModuleWeekCalendar`, which gets them from `GET /revision-sessions` for `weekCalendarRange` since it doesn't read `/calendar`.

**SubmodulePage.** Title edits inline in `PageHeader` (Enter/blur saves, Escape cancels); the settings dialog holds only delete.

## Lectures

Lectures with `feed_id` come from a calendar feed and are read-only: `splitFeedLectures` (in `lib/lectureSchedule.ts`) takes them out before `groupLectures` (timetables skip weeks, which would break its cadence inference) and the Lectures tab shows them as `FeedLectureCard`s (by feed + title, with the next date, the calendar's name and Unlink). Above them, `CalendarSeriesPicker` ("From your calendars") offers unlinked series whose title starts with the module's course code (one-click Link, via `linkFeedSeries`) and a Radix `Select` of every other unlinked series; `FeedLinksPanel` pre-selects the same suggestions. Lecture changes in the dialog call `onLecturesChanged` (refetch, dialog stays open); `onChanged` is the General save, which closes it. There is no backend recurrence rule. `ModuleSettingsDialog`'s Lectures tab creates one `Lecture` per occurrence (7 or 14 days apart, max 52) via repeated `POST /lectures`. `groupLectures` re-infers series on read: same title+location on a consistent 7/14-day cadence. Editing a series deletes all its lectures and recreates them.

`LectureSubmodules` shows a Lecture's covered Submodules as "Open notes" links plus a checkbox menu that saves each tick (feed lectures too); it's on the Overview Day agenda (expanded lecture), `ModuleDayList` and the Lectures tab (per-occurrence "Topics" list). Editing a manual series carries the topics over by position (`submoduleIdsByOccurrence`). SubmodulePage lists the lectures that covered it (`SubmoduleLectures`, via `lecturesCovering`).

## Settings dialogs

Both use the same category-sidebar shell.

- `ModuleSettingsDialog` (General, Lectures). The credits field is validated client-side against `max_credits` minus every other module's credits (its own `useAsync` calls); `AddModuleDialog` has no such check.
- `AppSettingsDialog` (Appearance, General, Keybinds, Calendars, AI Integration, Data; Data is a placeholder). Calendars is `CalendarFeedsSettings` (add a feed from a link or an uploaded `.ics` file; enable checkbox; Refresh for URL feeds, Replace file (hidden file input) for file feeds; "Last synced/updated X ago" via `lib/calendarFeeds.ts::formatSyncedAgo` and `last_error` as a warning; the list shows only the URL's host, since it's a secret; "Link to modules" opens `FeedLinksPanel`, one Radix `Select` per event series (`none` = not linked), saved as a whole through `setFeedLinks`) above `PersonalEventsSettings` (add/edit/delete personal events, form logic in `lib/busyTime.ts`); after each change either refetches its own list and calls `onCalendarChanged`, which Overview wires to `calendar.refetch`. The content pane scrolls on its own (`max-h` + `overflow-y-auto`, with `min-w-0` on it and its row so long rows truncate inside the dialog's grid). Appearance: theme/skin/`table_alignment` apply live on click; `note_font_size` (10–32) commits on blur. Keybinds: one `KeybindInput` per `KEYBIND_ACTIONS` entry; click to record, Escape cancels, `captureKeybind` emits `Mod-Shift-Alt-key` order; shows "Also used by X" on conflicts and a reset button when not default.
- Every `AppSettingsDialog` save calls `onChanged`, which refetches Overview's app settings in place (the dialog stays mounted). Controls read straight from the `settings` prop; only `max_credits` and `note_font_size` keep local drafts, reset each time the dialog opens.
- AI Integration is `AISettingsPanel`: a Claude/Gemini provider `Tabs` (switching saves that provider's first model from `GET /ai/models`; a key icon marks providers with a saved key), a write-only password input for the selected provider's key (always starts empty; Save/Remove), a Radix model `Select` filtered to that provider, and Test connection (`POST /ai/test`). Its state (`lib/ai.ts::AISettingsState`, built with `pickAISettings`) lives in the dialog's `aiSettings`, updated from each PATCH response and not re-seeded from the (stale) prop on reopen.
- **AI actions** elsewhere use `AIActionButton`: a normal `Button` when `ai_enabled`, otherwise disabled with a tooltip pointing to this tab. Show failures with `lib/ai.ts::aiErrorMessage` (AI errors arrive as `ApiError` with a readable `message` and a `kind`).
- **Submodule AI actions** share an "estimate → confirm → run" step: `lib/useSubmoduleSource.ts::useSubmoduleSource(submoduleId)` fetches `GET /submodules/{id}/ai-source` (re-fetching as raw-PDF opt-ins change) and returns `{ estimate, error, rawPdfIds, setRawPdf, ready }`; `components/SubmoduleSourcePanel` renders it (token estimate, large-request warning, one "send the original PDF instead" checkbox per near-empty PDF). Mount both only while the action's dialog is open (the first fetch converts Attachments), disable the run button until `ready`, and send `rawPdfIds` as `raw_pdf_ids`. `GenerateFlashcardsDialog` is the first user.

**Flashcard generation.** `GenerateFlashcardsDialog` (SubmodulePage header, "Generate cards") flushes the note via `beforeOpen`, then: count (1–30, `lib/flashcardReview.ts::clampCardCount`) + source panel → `POST .../flashcards/generate` → review list. Each proposal renders with `FlashcardFace` (the study session's card face, markdown + KaTeX) and can be accepted (created immediately via `createFlashcard` with `source: 'ai'`), edited (textareas, `validateEdit`) or rejected; "Accept all remaining" saves the pending ones in order. Closing never saves pending proposals; `onSaved` refetches on close if anything was saved. Review state helpers live in `lib/flashcardReview.ts`.

**Summaries.** `components/SubmoduleSummary.tsx`. `getSubmodule`/`updateSubmodule` return `SubmoduleDetail` (`summary_markdown`, `summary_stale`). With no summary, the SubmodulePage header shows "Summarize" (`AIActionButton`); once one exists, `SubmoduleSummary` renders it above the editor (collapsible, collapsed state in `localStorage`, `MarkdownView` for markdown + KaTeX) with Regenerate and a "Notes changed since this summary" badge when stale. Both open the controlled `SummarizeDialog` (source panel → `POST /submodules/{id}/summary`) after flushing the note; success refetches the Submodule. The stale badge updates on its own because note saves refetch.

## Theming

`lib/theme.ts`: `SKINS` (`default`/`slate`/`sepia`, CSS variables in `index.css` under `:root[data-skin="…"]` and `.dark`) and `applyTheme(mode, skin)`, which toggles `.dark` and sets `data-skin` (resolving `system` via `prefers-color-scheme`). `App.tsx` calls `useApplyTheme()` once. `index.css` also:
- sets `color-scheme: light`/`dark` so native date/time pickers, checkboxes etc. follow the theme;
- hides number-input spinners app-wide;
- styles a thin theme-aware scrollbar (it's the one users see while editing notes, since the editor doesn't scroll internally).

## Desktop shell (`frontend/src-tauri/`)

Optional dev-only Tauri wrapper around the same Vite dev server (`localhost:5173`). `pnpm tauri dev` from `frontend/` (starts the dev server itself; needs a Rust toolchain). `pnpm tauri build` produces `.deb`/`.rpm`; AppImage fails (linuxdeploy needs fuse2) and isn't a current goal.
